# Relecture C — sécurité, robustesse, collaboration, IA locale (Atelier v19, 30/10/2026)

Lecture seule du code ; vérifications réelles avec Playwright (éditeur servi sur :8791) et `php -S` (publish.php généré). Scripts : `scratchpad/audit/xss-i18n.mjs`, `php-checks.mjs`.

## 1. Résumé

- La base est saine : assainisseur à liste blanche rebâti de zéro (`core/sanitize.js`), URL filtrées, identités ECDSA P-256 avec défi signé des deux côtés, signalisation chiffrée AES-GCM (clé HKDF du secret de salle) que le serveur ne peut pas lire, jeton de publication jamais stocké en clair côté serveur (SHA-256 + `hash_equals`), publish.php qui refuse tout fichier exécutable et tout chemin douteux, journal qui masque e-mails, jetons et liens d'invitation.
- **Un vrai trou (bloquant)** : le texte riche n'est assaini qu'au rendu du canevas, pas à l'entrée. Le tableau des traductions fait `el.innerHTML = valeur brute` → un projet `.json` reçu d'un tiers, ou une modification envoyée par un pair « éditeur », exécute du script dans l'origine de l'éditeur, qui détient en clair (IndexedDB) le jeton de publication, le jeton GitHub et la clé privée. Reproduit : 2 exécutions à l'ouverture de 🌐 Traductions.
- **Important** : (a) `site.publish.url` n'est pas une partie privée pour la collaboration ni pour l'import → un pair ou un `.json` peut y mettre `https://attaquant/publish.php`, et le jeton retenu sur l'appareil est pré-rempli : un clic « Publier » l'envoie ailleurs ; (b) la boîte aux lettres de signalisation accepte sans jeton ni limite par adresse jusqu'à ≈ 1,3 Go (100 salles × 200 × 64 Ko), reproduit ; (c) publish.php répond `ok:true` alors qu'un fichier n'a pas pu être mis en place, reproduit ; (d) aucune demande de stockage persistant ni mesure du quota : IndexedDB est effaçable par le navigateur (Safari : 7 jours sans visite ; Chrome : pression disque), et les versions vivent dans la même base ; (e) aucun CSP, ni dans l'éditeur ni sur le site publié.
- IA locale : API actuelles de Chrome (`LanguageModel`, `Summarizer`, `Rewriter`, `Writer`, `Proofreader`, `Translator`, `LanguageDetector` avec `availability()` / `create()` / `monitor` / `responseConstraint`), pas de `window.ai` déprécié ; dégradation propre ; valeur réelle surtout pour Traduction et Corriger, mais conditionnée à Chrome sur ordinateur + 22 Go libres + GPU > 4 Go ou 16 Go de RAM, et à des flags pour Rewriter/Writer/Proofreader.
- Vie privée du site publié : très bon (façades au clic pour YouTube-nocookie, Vimeo dnt, Google Maps avec lien OSM ; aucun traceur), sauf les **polices Google chargées depuis fonts.googleapis.com** (jugement LG München 2022 : adresse IP transmise sans consentement) et le serveur STUN de Google pour la collaboration.

## 2. Points positifs (précis)

- Assainissement : `core/sanitize.js:8-11` liste blanche `p br strong em u a ul ol li`, contenu de `script/style/iframe/object/svg/math/template` supprimé en entier (l.11, 57-59), balises rebâties (l.79-80) donc aucun attribut ne passe sauf `href` filtré par `safeUrl` (`core/escape.js:14-23`, qui retire espaces et caractères de contrôle avant de lire le schéma : `java\nscript:` est bloqué). Rendu : `core/render.js:131-132` passe tout texte riche par `sanitizeRich/sanitizeInline`, attributs par `escapeAttr` (l.140-155), liens par `resolveLink` (l.130). Le DOM de l'éditeur est construit par `h()` sans innerHTML pour le contenu saisi (`editor/dom.js:1`), commentaires rendus en nœuds texte (`editor/review-ui.js:107-111`), sorties de l'IA échappées (`editor/inline.js:34, 282-296`).
- Publication : `core/publish.js:17-21` jeton 256 bits aléatoire ; seul son SHA-256 est écrit dans publish.php (l.52, 213-216 `hash_equals`) ; `sleep(1)` sur refus (l.245, 263). `check_path` (l.177-192) : chemins absolus, `..`, fichiers cachés, segments non ASCII, `atelier-data`, extensions exécutables même en double extension (`x.php.jpg`, l.188), liste blanche d'extensions (l.56). Dépôt en zone de transit puis `rename` (l.292-312) ; suppression limitée aux fichiers du manifeste précédent (l.314-321 : les fichiers ajoutés à la main par FTP sont gardés) et à l'intérieur de `realpath($root)`. Données privées `atelier-data/*.php` avec garde `<?php http_response_code(404); exit;` + `.htaccess` deny + `index.html` (l.59, 85-86, 154-158) : illisibles même si `.htaccess` est ignoré (nginx).
- Formulaire : honeypot `website` (l.358), 5 messages/heure par adresse hachée (l.373-379), `Reply-To` uniquement si `FILTER_VALIDATE_EMAIL` (l.368) donc pas d'injection d'en-tête, sujet nettoyé des caractères de contrôle (l.204-207, 383), redirection `_back` restreinte à un chemin relatif (l.344-345 : pas de redirection ouverte), adresses de destination jamais dans les pages (`forms.php` privé, l.325-335).
- Éditeur → serveur : HTTPS obligatoire sauf localhost (`core/site.js:295-296`) ; jeton en en-tête, jamais dans l'URL (`editor/publish-ui.js:105`) ; vérification du site avant envoi (l.90-91) ; jeton GitHub à portée fine recommandé dans l'interface (l.163).
- Collaboration : identité ECDSA P-256 (`core/review.js:12, 67-72`), empreinte liée à la clé publique (l.53-56) vérifiée à chaque hello (`core/collab-protocol.js:212`), défi signé des deux côtés avec nonce + salle (`review.js:93-96`, `collab-protocol.js:139, 230`), invitation signée par l'hôte avec rôle, salle, expiration 7 jours (`review.js:103-123`) et contrôle que l'hôte est bien le signataire (`collab-protocol.js:219, 225`). Signalisation chiffrée AES-GCM 256, IV aléatoire, clé HKDF (`review.js:132-147`) : le serveur ne voit ni SDP ni empreintes DTLS, donc pas d'homme du milieu sans le secret ; secret dans le fragment `#join=` (jamais envoyé au serveur, `review.js:125`). Rôles appliqués par l'hôte (`core/collab.js:263-286` : relecteur limité à `review`, chemins `__proto__` interdits, images vérifiées par `DATA_IMG`, taille bornée) ; commentaires signés et vérifiés (`review.js:154-168, 229-275`). Jamais d'adresse IP dans le journal (`editor/collab-net.js:7`).
- Stockage : images séparées du projet et écrites une seule fois (`editor/storage.js:39-61, 80-93`) ; versions sans duplication d'images (l.117-141) ; version de sécurité avant toute action risquée (`editor/versions-ui.js:42-44`) ; échec d'enregistrement signalé (« Non enregistré », `editor/store.js:76-80`).
- Journal : masquage par nom de clé et par motif (`core/log.js:16-21, 30-41` : hex 64, `?token=`, `#join=`, e-mails abrégés, data URL résumées) ; côté serveur, IP hachée avec le hash du jeton (`publish.js:452`), destinataire abrégé (l.70-73), contenu des messages jamais écrit ; lecture du journal serveur et diagnostic réservés au jeton (l.228-239, 244-245).
- IA : noms d'API actuels (`editor/ai.js:15-22, 164-171`), options de langue (`expectedInputs/Outputs`, l.28), schéma JSON strict (`responseConstraint`, l.207), session détruite après usage (l.209), suivi du téléchargement (l.120-128), causes d'échec expliquées en clair (l.37-43), matériel requis affiché (`editor/ai-ui.js:48`), faux modèle seulement via `window.__atelierAI` (l.25). « Demander à Atelier » n'exécute qu'un catalogue fermé d'actions (`core/assistant.js`) : une injection de prompt ne peut pas déclencher d'action hors catalogue.
- Vie privée du site : façades au clic (`core/widgets-extra.js:250, 277`), `youtube-nocookie` et `dnt=1` (l.72), carte Google avec alternative OpenStreetMap (l.304-305), affiche vidéo = image du site (l.275), aucun script tiers, aucun cookie.

## 3. Points négatifs

### Bloquant

**C-1 — XSS dans l'éditeur par texte riche non assaini à l'entrée (projet `.json`, opération de collaboration).**
Preuve : `editor/i18n-ui.js:64` `el.innerHTML = v;` avec `v = it.values[lang]` brut (l.53) ; `translatableItems` recopie `n.props[...]` sans nettoyage (`core/i18n.js:30-56`) ; `validateSite` ne contrôle que la structure (`core/site.js:346-384`) ; `normalizeSite` ne nettoie rien (l.100-114) ; `validateOps` ne nettoie pas les chaînes (`core/collab.js:263-286`) ; `load(doc)` à la réception d'un snapshot (`editor/collab-ui.js:71`).
Reproduit (`xss-i18n.mjs`) : projet exporté → `<img src=x onerror=…>` dans un texte riche → Fichier → Ouvrir : canevas sain (0 exécution), 🌐 Traductions : **2 exécutions** (cellules FR et EN).
Scénario : Laurent reçoit un `.json` « corrigé » par un tiers, ou un invité « éditeur » envoie l'opération ; dès que l'hôte ouvre les traductions, le script lit IndexedDB (`secrets` : `php-token`, `github-token`, `identity` avec la clé privée JWK, `editor/storage.js:174-188`), publie ce qu'il veut sur le site réel ou pousse sur GitHub, signe des commentaires au nom de l'hôte.
Correction : (1) `cellEditor` : `el.innerHTML = it.kind === 'inline' ? sanitizeInline(v) : sanitizeRich(v)` ; (2) assainir à l'entrée : une passe `sanitizeSiteTexts(site)` (parcourt `fieldsOf(type)` : `richtext` → `sanitizeRich`, `inline` → `sanitizeInline`, `text` → sans `<>`), appelée dans `normalizeSite` ou dans `load()`, à l'import, à la réception d'un snapshot, et sur les valeurs des ops reçues (`_incoming`) ; (3) test unitaire qui parcourt tous les `innerHTML` de `editor/` (grep dans un test) et exige qu'ils soient précédés d'un assainisseur ou d'une constante.

### Important

**C-2 — `publish.url` modifiable par un pair ou un `.json`, jeton pré-rempli : exfiltration du jeton en un clic.** `IGNORED_TOP = ['collab']` seulement (`core/collab.js:12`) : un éditeur invité peut écrire `site.publish.url` ; l'import ne passe pas par `setPublishSettings` ; la fenêtre Publier pré-remplit l'adresse depuis `state.site.publish.url` (`editor/publish-ui.js:41`) et le jeton depuis `getSecret('php-token')` (l.44) ; `run()` revalide seulement la forme `https://…/publish.php` (`core/site.js:295`) et envoie `X-Atelier-Token` à cette adresse (l.105). Même mécanique pour le jeton GitHub avec `gh.owner/repo` (publier dans le dépôt de l'attaquant). Correction : ajouter `publish` à `IGNORED_TOP` (réglage par appareil, pas partagé) ; retenir le jeton **par origine** (`setSecret('php-token:' + origin)`) et ne le pré-remplir que si l'origine correspond ; au premier envoi vers une nouvelle origine, demander confirmation explicite (« Vous allez publier sur www.x.be — première fois »).

**C-3 — Boîte aux lettres de signalisation : remplissage disque et CPU sans jeton.** `signal_post` (`publish.js:409-436`) : aucune authentification (voulu, l'invité n'a pas le jeton), aucune limite par adresse, plafonds 100 salles × 200 messages × 64 Ko ≈ 1,3 Go, et chaque dépôt/relève relit et réécrit tout le fichier de salle (`read_private`/`write_private`, l.429-432). Reproduit : 12 dépôts de 64 Ko acceptés sans jeton, fichier de 769 Ko. Le TTL de 15 min (l.396, 405-407) limite dans le temps mais pas l'instant. Correction : limite par adresse hachée (comme `rate.php`), plafond par salle en octets (p. ex. 2 Mo), `SIGNAL_SIZE` à 16 Ko (une offre SDP tient en 4-8 Ko), et « jeton de salle » : l'invitation (signée) contient déjà l'id de salle ; exiger dans le POST une preuve dérivée du secret (p. ex. HMAC du jour) que seuls les invités ont. 

**C-4 — Publication partielle annoncée comme réussie.** `publish()` compte les échecs de `rename` (`publish.js:304-309`) mais répond `200 {ok:true}` (l.336-337) ; l'éditeur affiche « Site publié : N fichiers ». Reproduit (`php-checks.mjs`) : un fichier régulier `css` bloque `css/site.css` → HTTP 200, `ok=true`, `written=2`, `php.publish.move-fail` dans le journal serveur seulement. Correction : si `$moved < count($new)` → 500 avec la liste, ne pas écrire le manifeste tel quel ; l'éditeur affiche l'erreur et la référence.

**C-5 — Stockage local effaçable, sans alerte.** Aucun `navigator.storage.persist()` ni `estimate()` (grep vide), aucun `beforeunload` ; tout (projet, versions, images, secrets) est dans la même base `atelier-v2` (`editor/storage.js:8-12`). Safari/iOS efface le stockage script après 7 jours sans visite ; Chrome évince sous pression disque ; une base pleine → « Non enregistré » (`store.js:76-80`) mais la fermeture de l'onglet perd tout depuis le dernier enregistrement. Les images supprimées du projet restent dans le magasin pour toujours (seul l'auto-test nettoie : `editor/selftest-safe.js:63-64`) → la base grossit jusqu'au quota. Correction : demander le stockage persistant au premier enregistrement et afficher l'état (persisté / quota utilisé) dans Site ; `beforeunload` si « Modifié »/« Non enregistré » ; ramasse-miettes des images orphelines après élagage des versions ; copie de secours automatique hors navigateur (cas d'usage §5).

**C-6 — Secrets en clair dans IndexedDB, sans CSP.** `secrets` contient jetons et clé privée JWK (`editor/storage.js:179-188`, `editor/collab-ui.js:36`) ; `index.html` n'a aucune `Content-Security-Policy` (grep vide) ; `publish.php` répond `Access-Control-Allow-Origin: *` (l.134). Conséquence : toute XSS (C-1 ou future) = vol immédiat, et un éditeur hébergé sur le même domaine que le site (`/atelier/`) partage son origine avec le site publié. Correction : CSP stricte dans l'éditeur (`default-src 'self'; connect-src 'self' https: wss:; img-src 'self' data: blob:; frame-src 'self' blob:; script-src 'self'` — le canevas `srcdoc` hérite du CSP, à vérifier avec les polices), héberger l'éditeur sur un autre hôte que le site (sous-domaine `atelier.`), chiffrer les secrets avec une clé dérivée d'un code à 6 chiffres demandé à la publication (optionnel).

**C-7 — Site publié sans en-têtes de sécurité.** Aucun `.htaccess` ni CSP dans le rendu (grep vide dans `core/render.js`, `core/zip.js`) ; publish.php refuse d'ailleurs tout fichier caché (l.184) donc l'utilisateur ne peut pas en déposer un par l'éditeur. Correction : publish.php écrit lui-même à la racine un `.htaccess` connu et sûr (`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy` compatible avec les façades et les polices choisies, HSTS si HTTPS) ; export .zip : fichier `.htaccess` + note pour nginx.

**C-8 — Polices Google chargées depuis Google sur le site publié.** `core/theme.js:18-20`, `core/render.js:425` (`preconnect fonts.gstatic.com` + feuille `fonts.googleapis.com`) : l'adresse IP de chaque visiteur part chez Google avant tout consentement — précisément le cas condamné par le LG München I (20/01/2022, 3 O 17493/20, 100 € de dommages) ; aucune mention de confidentialité ni page légale générée. Correction : télécharger les fichiers woff2 à l'export (`fonts.googleapis.com` → CSS → `fonts.gstatic.com`, à faire depuis le navigateur de l'éditeur ou fournir un lot embarqué des polices proposées), les ranger dans `assets/fonts/` et ajouter `woff2` à `ALLOWED` de publish.php (version 5) ; générer une page « Vie privée » depuis les réglages (formulaire → relais e-mail, façades, pas de cookie, hébergeur).

**C-9 — Mode relecture : l'invité fait confiance à tout ce que l'hôte envoie.** `onRemote` → `load(doc)` sans `validateSite` (`editor/collab-ui.js:71`) ; un document malformé casse le rendu (`canvas.load` échoue). Correction : `validateSite(normalizeSite(doc))` + assainissement (C-1) avant `load`.

### Mineur

- **C-10** Expéditeur du formulaire dérivé de `HTTP_HOST` (`publish.js:381-384`) : reproduit avec `Host: www.attaquant.example` → `From: Site <noreply@attaquant.example>` (sur un vhost par défaut) ; et de toute façon `noreply@<domaine>` sans SPF/DKIM configurés → courriers en spam. Correction : domaine d'expédition écrit en constante à la génération (depuis `baseUrl`) ; conseil SPF dans le guide.
- **C-11** `?atelier_debug=1` sans jeton renvoie la trace (`publish.js:67, 145`) : hash d'adresse, UA, mémoire ; statut sans jeton expose `PHP_VERSION` (l.227). Réserver la trace au jeton ; retirer la version PHP du statut public.
- **C-12** `rate.php` lu/écrit sans verrou (l.375-379) : deux envois simultanés peuvent passer sous la limite. Utiliser le même `flock` que la signalisation.
- **C-13** Invitations non révocables individuellement (`review.js:103-123` : pas d'identifiant ni liste de révocation) ; seule issue : fermer la session. Ajouter `jti` + liste `revoked` chez l'hôte.
- **C-14** Serveur STUN Google par défaut (`editor/collab-net.js:16`) : adresse IP des participants transmise à Google ; pas de TURN → échec sur NAT symétrique (4G/5G, CGNAT, entreprise) honnêtement diagnostiqué (l.95). Proposer un STUN/TURN européen (coturn chez OVH, ou le STUN d'un opérateur) dans le réglage, avec TURN authentifié par jeton temporaire.
- **C-15** Export SVG impossible : `editor/images.js:42` refuse `image/svg+xml` et publish.php n'autorise pas `.svg` (l.56) : les logos vectoriels sont pixellisés en WebP 1600 px (flou sur écrans denses pour un logo). Accepter le SVG après assainissement (DOMPurify-like maison : retirer `script`, `on*`, `foreignObject`, `href` externes) — sinon documenter.
- **C-16** Messages d'erreur de publish.php en français (`out(400, …)` partout) affichés tels quels dans l'interface EN/JA (`publish-ui.js:110`). Ajouter un `code` machine à chaque erreur et traduire côté éditeur.
- **C-17** Historique d'annulation : `applyRemote` réécrit tous les états passés (`store.js:113-114`) : O(150 × ops) à chaque réception ; acceptable aujourd'hui, à surveiller avec des sessions longues.
- **C-18** Import `.json` sans plafond de taille ni `try` autour de `normalizeSite` sur des types inattendus (`editor/app.js:211-213`) ; `JSON.parse` d'un fichier de plusieurs centaines de Mo gèle l'onglet. Refuser > 200 Mo et prévenir.
- **C-19** Pas de sauvegarde côté serveur ni d'historique des publications : une publication d'un site vidé écrase le site en ligne, la seule remise est locale (versions). Voir cas d'usage « sauvegarde sur l'hébergement ».
- **C-20** IA : `Rewriter/Writer/Proofreader` demandent des flags `chrome://flags` (`editor/ai.js:18-20`) : un non-informaticien n'y touchera pas ; le guide doit présenter ces fonctions comme « bonus » et garder Traduction + Corriger (Prompt API) en voie principale. Le contenu du site est injecté tel quel dans les prompts (`core/ai-tasks.js`) : une page contenant « ignore les consignes… » peut fausser une proposition, sans autre effet (sorties affichées, pas exécutées).
