# Cycle 27 — Photos sans douleur

## Demande
Audit du 30/10/2026, constats N2 (bloquant : « les photos font ramer puis planter l'éditeur ») et N26 (chaque frappe régénère toute la page et reconstruit l'inspecteur), § 6.3 « Cycle 27 » : P1 (images hors du modèle), P2 (rendu ciblé), Q7 (fixtures de projets anciens et schéma versionné). C'est la fondation du site touristique de Kumakōgen (15 photos et plus) et de la visite guidée.

## Spécification
- **P1 — Images hors du modèle.** `site.assets[id]` ne garde que `{ file, mime, width, height, variants: [{ w, file }], kind }` ; les octets vivent dans un magasin (`core/asset-store.js` : `put(id, { dataUrl | blob, variants })`, `get(id, w)`, `url(id, w)`, `has`, `delete`, `list`, `bytes()`, en mémoire ; l'éditeur en a une instance, `editor/assets.js`, persistée dans IndexedDB par `editor/storage.js`). Le rendu reçoit un résolveur `ctx.asset(id, w)` : `blob:` mis en cache (révoqué à la suppression) dans le canevas, `assets/<fichier>` à l'export. Aucune copie de site ne recopie d'octets (`cloneSite` partage `assets`, `fonts`, `icon`). Historique : états qui partagent les images, borné à 150 pas **et** 40 Mo (taille JSON hors images). `.json` autonome (octets réinjectés en `dataUrl`, séparés à l'ouverture). `.zip`, publication, versions, collaboration, auto-test et démonstration inchangés pour la personne.
- **P2 — Rendu ciblé.** `renderNode(site, page, id, opts)` (`core/render.js`) = exactement le fragment de `renderPage` pour ce nœud (même contexte : largeur, empilement, langue). Le canevas remplace seulement le nœud modifié quand la modification le dit (`opts.node` : frappe, réglage de contenu ou de style d'un élément) ; rendu complet sinon (structure, page, langue, appareil, composants partagés, en-tête/pied, édition de zone, modification distante). Frappe dans la page : l'inspecteur n'est pas redessiné, seule la valeur du champ correspondant suit (`inspector.sync`).
- **Q7 — Schéma versionné.** `site.schema` (3) ; `MIGRATIONS` numérotées appliquées par `migrate(site)` dans `normalizeSite(site, { assets })` ; projet sans `schema` = schéma 2 (cycles 1 à 26) ; schéma futur refusé par `validateSite` avec un message clair.

## Livré
- **Mesures** (Chromium sans écran, 10 photos de 600 Ko et leurs variantes, 7,7 Mo d'octets) : frappe dans la page **≈ 1 ms** médiane de `commit` à l'affichage (avant : 172–230 ms) ; frappe dans l'inspecteur ≈ 1 ms ; tas JS **6 → 9 Mo** après 300 modifications (avant : 1 033 Mo après 150) ; JSON du projet en mémoire 16 Ko ; 0 `inspector.render` et `<main>` jamais remplacé pendant 20 frappes ; collaboration : projet et 10 photos chez l'invitée en ≈ 2 s.
- `core/asset-store.js` (magasin, `cloneSite`, `absorbAssets`, `inlineAssets`, `pruneStore`) ; `editor/assets.js` (instance de l'éditeur).
- `core/site.js` : `SCHEMA`, `MIGRATIONS`, `migrate`, `normalizeSite(site, { assets })`, `addAsset(site, img, store?)` (sans magasin : ancien comportement, data URL absorbée au `commit`), `removeAsset`, polices recréées au lieu d'être modifiées en place ; toutes les copies de site du cœur passent par `cloneSite` (`site.js`, `collections.js`, `components.js`, `presets.js`, `i18n.js`, `layout.js`, `menu.js`, `review.js`, `seo.js`, `versions.js`, `a11ypage.js`, `colors.js`, `legalpages.js`, `tokens.js`).
- `core/render.js` : option `assets` de `renderPage`, `renderSite`, `buildCss`, `makeContext` (`ctx.asset(id, w)`) ; noms publiés inchangés (empreinte calculée sur les octets du magasin) ; `renderSite` renvoie aussi `missingAssets` ; `renderNode(site, page, id, opts)` (l'ancienne forme `renderNode(node, ctx)` reste).
- Éditeur : `store.js` (absorption au `commit`, à `load` et à `applyRemote`, historique borné, `perf.commit`, ménage des octets protégé pendant l'auto-test), `storage.js` (`splitAssets(site, store)` lit le magasin), `canvas.js` (rendu ciblé), `inspector.js` (`inspector.sync`), `inline.js`/`fields.js`/`styletab.js` (`opts.node`), `app.js` (`.json` autonome, `.zip` et aperçu avec le magasin), `publish-ui.js`, aperçus d'images (`fields.js`, `seo-ui.js`, `smart-ui.js`, `ai.js`).
- Collaboration : les opérations ne portent que les métadonnées ; octets dans des messages `asset` (après le projet complet pour un nouvel invité, avant les opérations qui ajoutent une photo, relayés par l'hôte) et `asset-req` (images manquantes) ; images des relecteurs refusées ; `collab.asset.*`.
- Guide : 1.3 et 1.4 (images dans le `.json`, schéma, projet trop récent), 4.34 (photos sans ralentir), 10.13 (photos en collaboration), codes `asset.*`, `perf.commit`, `inspector.sync`, `collab.asset.*`, `export.zip.missing-images` ; traductions `i18n/parts/M-images.*.json`.

## Limites
- L'inspecteur suit la frappe dans la page pour les champs simples ; un élément de liste (carte d'une galerie, question d'une FAQ) est mis à jour à la sélection suivante.
- Rendu ciblé seulement pour la page elle-même : dans un composant partagé, l'en-tête, le pied, une carte ou une page de détail, le contenu est rendu en entier (comme avant).
- Le magasin garde en mémoire les photos de la séance tant que l'historique ou un instantané (auto-test) les référence ; aucune interface ne supprime encore une image du projet (`removeAsset` existe dans le cœur).
- Les polices importées (`site.fonts`) et l'icône (`site.icon`) gardent leurs octets dans le projet : elles sont partagées entre copies (plus de recopie), pas encore rangées dans le magasin.
- En collaboration, une photo très lourde passe en plusieurs morceaux par le canal ; au-delà de 4 Mo en attente, l'envoi se met en pause puis reprend (`rtc.flow.*`).
